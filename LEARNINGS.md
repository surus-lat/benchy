# LEARNINGS — what the bare metal actually is, under loss-first

## TASK — zero engine code, and a caveat

The `task` key was deleted from bench.json (cycle 7): the engine never read
it, and the schema is visible in the cases — `in` values show the input type,
`want` values show the output vocabulary. Under loss-first, the TASK pillar
needs ZERO engine code: the task lives entirely inside the data.

Caveat (recorded, cycle 7): cases carry the task only by EXAMPLE. A
task-only description ("takes pdf, returns extracted_fields[json]") with no
cases yet cannot be expressed — the schema only becomes visible when the
first case exists. This is a real limitation for the CREATE-new-benchmarks
flow (you want to write the task before collecting data). Noted for unify,
not re-added: re-adding an unread key would be noise. Unify should decide
whether a task description is a first-class field or a README-style comment.

## SCORING — the pillar with the most metal

Three pieces of metal, all proven by deletion:

- The `scoring` key + its load-time check (cycle 11, BARE_METAL). Law #6
  makes scoring a pillar of the benchmark identity; the key is the seat
  where the author NAMES the policy; the check is live honesty code (unknown
  scoring fails loud, never silently exact-matches). Deleting it stayed
  green — the guard was UNGUARDED. Fixed by adding the guard test.
- The `1.0 - score` inversion (cycle 14, BARE_METAL). Lower=better is not a
  convention, it is OPTIMIZER SEMANTICS: prompt-optimizers minimize;
  `loss(s) < loss(best)` must mean "s is better". The inversion is the
  bridge between the exam view (score: higher=better) and the loss view.
- The `float()` cast on per-case verdicts (cycle 15, BARE_METAL). Artifact
  boundary armor: without it, verdicts become JSON booleans (`"score": true`
  — an unstable schema for a software-3.0 optimizer) and realistic
  numpy/pandas systems (np.bool_) CRASH json.dumps on the trace. Deleting it
  stayed green because `True == 1.0` — guard unguarded AGAIN (same shape as
  cycle 11). Guard test added; deletion now fails.

The engine interprets exactly ONE scoring ({"compare": "exact",
"aggregate": "mean"}) — vocab tables were deleted (cycle 5) because nothing
used the extra vocabulary. The vision's weighted/hierarchical scorings are
NOT built; the load-time check is the honest placeholder that fails loud
until they are.

## DATA — the artifact is the exam's memory

- bench.json = {path, scoring, cases}. Nothing else survived: the `task`
  key (cycle 7) and the receipt `i` index (cycle 6) were noise.
- loss.trace = {score, cases:[{in, want, got, score}]} is EVIDENCE ONLY
  (cycle 9 deleted the path key from it — identity is the closure itself).
- `want` in the trace is metal (cycle 10): the artifact must be
  SELF-CONTAINED — interpretable ALONE by a human or a software-3.0
  optimizer. A failed case without `want` reads "wrong, but about what?"
  Derivable-from-source is not the bar.
- Empty cases: ZeroDivisionError, loud by construction (cycle 15) — zero
  guard code needed. Missing cases: KeyError, also loud. Honesty can be free.

## SYSTEM — zero engine code, and the reason why

`system()` was deleted (cycle 8). A system is ANY callable
`solve(input) -> prediction`; stdlib importlib is the loader. Model, node,
workflow, agent — the engine cannot tell them apart and must not try. The
SYSTEM pillar is a PROTOCOL (the loss's argument), not a module. This is the
deepest cut the loss-first angle made: `(System) -> float` IS the AI-API.

## did the angle survive?

SURVIVED. The falsification test was: "the exam/report side needs concepts
the loss view cannot generate." It never fired. The graded artifact is
`loss.trace` — an attribute of the loss itself, not a separate concept. The
exam (cases), the report (per-case verdicts + aggregate), and the ranking
are all generated BY one evaluation of `(System) -> float`. Every concept
the exam side wanted (Bench class, run(), as_loss(), artifact builder,
system loader, CLI) dissolved into the closure or into test-side code.

The six BARE_METAL badges are the surviving metal: want-in-trace (10),
scoring key + check (11), the loss closure (12), the trace home (13), the
loss direction (14), the verdict cast (15). Four of the six live on the
loss/closure; the other two live at the artifact boundary.

## what the badges mean for the other nine searchers

1. ARTIFACT SELF-CONTAINMENT (want, cycle 10): your graded artifact will be
   consumed by optimizers with no access to your source data. Anything the
   artifact needs to be INTERPRETED — the target answer especially — must be
   IN the artifact. "It's derivable from the benchmark file" is not a
   defense.
2. HONESTY GUARDS NEED GUARD TESTS (scoring check, cycle 11; float cast,
   cycle 15): twice, deleting a pillar kept every test green because nothing
   guarded the guard. If a deletion stays green but your judgment says the
   concept is metal, ADD THE TEST FIRST, delete again — then the badge is
   earned, not asserted. Green-on-delete proves either noise or an unguarded
   guard; only judgment tells them apart.
3. CLOSURE STATE IS LOAD-BEARING (cycles 12-13): the receipt must be
   per-instance (two benchmarks must not clobber each other) and the loss
   signature must stay pure `(System) -> float` (optimizers must get a
   scalar, nothing else). Whatever your shape, those two constraints force
   per-benchmark state that is invisible to the calling convention.
4. DIRECTION IS SEMANTICS (cycle 14): if you return score instead of loss,
   every downstream optimizer inverts meaning for your one callable. Pick
   lower=better and bridge it explicitly.
